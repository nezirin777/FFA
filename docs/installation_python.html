FFA Python版 設置・運用手順書

現行Ver3をWindows + Apache CGI環境へ設置し、初回動作確認・更新・保存データ保護を行うための手順

資料一覧設置・運用手順装備カタログ職業カタログモンスターカタログキー・能力値辞典戦闘仕様書チョコボ仕様書移行・保存形式仕様書管理・運用手順書セキュリティ仕様書コマンドフローチャート
この資料はリポジトリ直下を実行ルートとする現行Ver3向けです。旧版_ver1・旧版_ver2は移行・参照用であり、通常運用時に公開する必要はありません。設置先のURLやPythonの実行パスは環境に合わせて読み替えてください。

1. 動作要件

項目要件・確認内容
PythonPython 3.x。CGI入口であるlogin.py、chara_make.py、admin.py、others.pyの先頭にあるshebangの実行パスが、設置先のPython実行ファイルと一致していること。
WebサーバーApache 2.4など、PythonをCGIとして起動できるWebサーバー。常駐WSGIアプリケーションは現行の前提ではない。
外部ライブラリJinja2。sub_def/common.pyとsub_def/utils.pyがテンプレート描画に使用する。
文字コードソース、テンプレート、JSON、HTMLをUTF-8で扱う。日本語ファイル名を含む画像・データがあるため、OS・Apache・Pythonの文字コード設定を確認する。
書き込み権限Apacheの実行アカウントがsave_data、lock、backupsへ読み書きできること。

python -m pip install Jinja2 python -c "import jinja2; print(jinja2.__version__)"

依存ライブラリは、Apacheが実際に使用するPython環境へインストールしてください。別のPythonへインストールしてもCGIから見えない場合があります。

3. Apache CGIの設定

ApacheのDocumentRootまたはAliasから、FFAのリポジトリ直下をWebルートとして参照します。既存のApache構成に合わせてパスを変更してください。

<Directory "D:/Apache24/htdocs/Antigravity/FFA"> Options +ExecCGI AllowOverride None Require all granted AddHandler cgi-script .py DirectoryIndex index.html </Directory> # Windows版Apacheでshebangを使う場合の例 ScriptInterpreterSource Script
WindowsのApacheでのPython実行方法は、Apacheのビルド・サービスアカウント・Pythonのインストール方法で変わります。次の4ファイルをテキストエディタで開き、先頭行のshebangにあるD:\Python\Python314\python.exeを、設置先で実際に使用するPythonのフルパスへ揃えてください。
login.py ／ chara_make.py ／ admin.py ／ others.py
パスを変更した後は、4ファイルすべてを対象にCGI実行確認を行います。

公開範囲の注意

Webルート直下に置く構成でも、次の場所はHTTPから読めないようにしてください。Apacheの設定、Aliasの分離、アクセス拒否のいずれかを使います。

save_datalockbackupstemplates旧版_ver1旧版_ver2tools.git

特にsave_dataにはパスワードハッシュ、セッション関連情報、個人データが含まれます。静的JSONの直接公開を許可しないでください。

4. config.pyと環境設定

config.pyはファイル自身の場所を基準に主要パスを組み立てます。設置場所を変更しても、通常は相対パスを手作業で大量に書き換える必要はありません。

設定現行の役割本番での確認
save_dirユーザー保存と共有保存のルート。Apacheに書き込み権限を付与し、HTTP公開を禁止する。
lock_dir排他ロックの保存先。Apacheに書き込み権限を付与する。古いロックが残った場合は原因確認後に整理する。
template_dirJinja2テンプレートの読み込み先。実行ルートからの位置関係を変えた場合は、テンプレートエラーを確認する。
backup_dir日次バックアップの保存先。save_dataの外に置く。Apacheから書き込み可能だがHTTP公開しない。
FFA_SECRET_KEYログインセッションとCSRFトークンの署名に使う秘密鍵。本番では十分に長くランダムな環境変数を設定する。変更すると既存セッションが無効になる。
FFA_ADMIN_PASSWORD管理画面の認証に使うパスワード。既定値のまま運用しない。環境変数または安全な設定方法で変更する。
maintenance_modeログイン後のゲーム処理を停止するメンテナンスフラグ。大規模更新、バックアップ復元、保存形式変更の前後に利用する。
秘密情報の注意: FFA_SECRET_KEYとFFA_ADMIN_PASSWORDはソース、公開設定、Git履歴、バックアップ資料へ書き込まないでください。既定値は設置確認用に過ぎず、本番用の値ではありません。

5. 初回設置手順

順番作業確認ポイント
1リポジトリを設置先へ配置する。config.pyと各CGI入口が同じルートにあること。
2PythonとJinja2を、CGIが使用するPython環境へ導入する。python -c "import jinja2"が成功すること。
3login.py、chara_make.py、admin.py、others.pyの先頭行を確認し、shebangのPython実行パスを設置先のフルパスへ変更する。続けてApacheのCGI設定を合わせる。4ファイルすべてがCGIとして実行されること。ブラウザで開いたとき、PythonソースのダウンロードではなくHTMLが返ること。
4save_data、lock、backupsを作成し、Apache実行アカウントへ権限を付与する。ログイン、キャラクター作成、保存、ロック作成が成功すること。
5秘密鍵・管理者パスワードを環境変数へ設定する。設定後にログインセッションと管理画面認証が成功すること。
6index.htmlまたはothers.pyへアクセスする。トップ、ログイン、キャラクター作成、街、CSS、画像が表示されること。
7保護されたテストユーザーで一通り操作する。宿屋、装備、銀行、掲示板、モンスター戦、チョコボ牧場、ログアウトを確認する。
8Apacheのアクセスログ・エラーログを確認し、テストデータと本番データを分ける。500エラー、権限エラー、テンプレートエラー、JSON破損がないこと。

同梱のdev_server.pyはローカルでCGI経路を確認するための簡易サーバーです。本番のApache設定や権限を再現するものではありません。

python dev_server.py # 表示されたURL例: http://localhost:8000/login.py

6. 更新・マイグレーション手順

  1. 利用者へメンテナンス時間を告知し、maintenance_modeを有効にする。
  2. 現行のsave_dataとbackupsを別媒体へ退避する。
  3. コード、テンプレート、静的ファイル、マスターデータを更新する。
  4. 旧版データを取り込む場合は、コピーした作業用データに対して変換スクリプトを実行する。原本を直接変換しない。
  5. 変換結果のuser_all.json、装備ID、職業ID、能力値キー、倉庫、チャンプ、共有データを検証する。
  6. テストユーザーでログインから各施設まで確認し、Apacheログに異常がないことを確認する。
  7. 問題がなければmaintenance_modeを無効にして公開する。問題があれば現行データを上書きせず、バックアップから復元する。
変換元用途注意
旧版_ver1/セーブデータ移行用ファイル/convert_to_ver2.py旧版Ver1の個別ログをVer2形式へ変換する。Ver1原本を複製して作業する。変換元のファイルが不足している場合は空データとして進めず、結果を確認する。
旧版_ver2/change_data/convert_all.pyVer2データを現行Ver3の保存形式へまとめて変換する。旧キーをそのまま出力せず、現行のキー順・キー名・装備・倉庫形式に一致することを確認する。

変換スクリプトは通常のゲーム実行に必要なモジュールではありません。運用中の公開URLから直接実行できない場所に置き、作業前後のバックアップと検証結果を残してください。

7. 日次バックアップと復元

現行版はcronや常駐プロセスではなく、ログイン処理を契機にその日の最初のバックアップを作成します。backups/YYYY-MM-DDへ保存し、最大40日分を保持します。

通常運用

ログインが成功したときに日次バックアップを確認します。同日中は二重作成せず、古い日付のバックアップを保持日数に応じて整理します。

管理画面からの復元

復元前にメンテナンスモードを有効にします。現行データは復元前退避へ移されるため、復元後の確認が終わるまで削除しません。

保護ユーザー

protected_user_idsのユーザーは放置削除・管理画面削除から除外されます。保護ユーザー用の復元元は自動作成ではなく、別途用意したファイルを使います。

バックアップの扱い: バックアップはパスワードハッシュやプレイヤーデータを含む運用データです。Web公開、Git登録、無制限の共有をしないでください。ディスク障害対策として、必要に応じてWebサーバー外・別媒体へ複製します。
